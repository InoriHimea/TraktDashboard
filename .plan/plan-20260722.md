# Plan 2026-07-22 — 观看历史永久保留 + 反向恢复到 Trakt

## 背景

用户反馈 Trakt.tv 上的观看历史被外部 `jellyfin-plugin-trakt-ex` 插件用错误的
Jellyfin 数据覆盖、丢失了历史记录（外部仓库的问题，用户自行去那边排查）。借
着这次事件，用户明确了两条本项目必须满足的原则：本地 `watch_history` 应该是
永久档案，不能因为"Trakt 上暂时看不到了"就跟着清掉；必要时还要能把本地留着
的记录反向推回 Trakt。

## 批次一 — 本地永久保留（修复既有违反者）`[x]`

审计发现唯一违反"本地永不删除"原则的代码：`services/sync.ts` 的 `syncMovies`
每次同步都会把本地"Trakt 现在报告的历史里已经找不到"的电影观看记录直接删掉
（`staleTraktHistoryWhere` + `db.delete(watchHistory)`）。这段逻辑只删本地镜
像、从不调用 Trakt 删除接口，所以不是"错误覆盖 Trakt"这类问题，但确实违反了
"本地也不应该删除"这条新原则。

- [x] 删除 `syncMovies` 里的 `staleTraktHistoryWhere` 查询+删除整段逻辑，以
      及只在这段逻辑里用到的 `remoteTraktPlayIds` 变量。
- [x] 更新 `sync-movies.test.ts` 五处涉及 `selects` 数组的测试（移除"stale
      rows"那一格），把原本断言"会删除"的用例改写成断言"绝不删除"（哪怕
      Trakt 完全不报告任何历史，本地记录也纹丝不动）。
- [x] 同步修掉 `p2-api-flows.test.ts` 里一个断言旧删除行为的用例
      （`deleteWhereCalls` 从期望 1 次改成期望 0 次）。
- [x] **踩坑**：`syncMovies` 的 Trakt 拉取失败会直接 `return` 提前退出，根本
      不会走到（已删除的）那段删除逻辑——所以这条清理路径本身没有"部分失败
      误删"的风险，删掉它不需要额外的容错设计。

验收：api 823 个测试全绿，覆盖率 86.17/73.14/87.69/87.93（stmts/branch/
funcs/lines），仍高于阈值 86/73/87/87，未触发 ratchet（略微下降符合预期——
删代码本身会略微收缩覆盖率的分子分母）。

## 批次二 — 反向恢复到 Trakt `[x]`

做批次一时顺带发现：应用内"标记已看"按钮（`shows.ts` 的 `POST .../watch`
路由）从来没推送过 Trakt，只写本地 `source='manual'`——这和"曾经在 Trakt、
后来丢了"（`source='trakt'` 但 `trakt_play_id` 现在查不到）是两种不同情况。
跟用户确认后，两种都覆盖，用一个开关区分：默认只处理"Trakt 来源、现在拉不到
了"的记录，用户可以勾选把"本地手动标记、从未同步"的记录也纳入候选一起恢复。
`source='import'`（JSON 导入）的记录不在范围内。

关键发现（决定实现方式，详见 `/Users/inorihimea/.claude/plans/delightful-humming-avalanche.md`
存档的完整计划）：Trakt `POST /sync/history` 的响应只返回计数
（`{added, not_found}`），不返回新记录的 id（`trakt/trakt-api#248` 至今是开放
的 feature request）；同一来源也证实这个端点偶发 500。所以推送成功后必须再
调一次 `getHistory` 用 `watched_at` + 该集/电影自己的 trakt id 精确匹配回填
新 `trakt_play_id`，匹配不到的算 `unconfirmed`（不是失败，也不假装成功）；
写路径逐批 try/catch，一批失败不阻塞其余批次（复用 `duplicates/remove` 已有
的容错设计）。

- [x] `services/trakt.ts` 新增 `addToHistory(userId, {movies, episodes})`，
      `POST /sync/history`，新类型 `TraktAddHistoryItem`/`TraktAddHistoryResult`。
- [x] 新增 `services/history-restore.ts`：
      `findRestorableHistoryEntries(userId, includeManual)`（现拉 Trakt 完整
      历史比对本地）+ `restoreHistoryEntries(userId, ids)`（分批推送 + 事后
      用 `getHistory` 精确匹配回填 id）。
- [x] `routes/history.ts` 新增 `GET /restorable?includeManual=false`、
      `POST /restore`。
- [x] `packages/types` 新增 `RestorableHistoryEntry`/`RestoreHistoryResult`。
- [x] `lib/api.ts`/`queryKeys.ts`/`hooks/index.ts` 新增
      `history.restorable.list/restore`、独立 query key 族
      `historyRestorable`、`useRestorableHistory`/`useRestoreHistory`。
- [x] 新页面 `pages/HistoryRestorePage.tsx` + 路由 `/history/restore`：
      `includeManual` 开关、本地化名称展示（复用查重页同款
      `translatedXxx??原始` 惯例）、来源标签（"Trakt 曾同步现已找不到" /
      "仅本地标记，从未同步"）、多选 + `ConfirmDialog`（`confirmColor="violet"`
      而非 `"rose"`——这是写入不是删除）、`restored`/`unconfirmed`/`failed`
      三态 toast。默认不预选任何条目（比查重页更保守——这是新写路径，不用
      "疑似 bug"这种默认建议逻辑）。
- [x] `HistoryPage.tsx` 头部按钮组，"查重"旁边加"找回丢失"入口。
- [x] `zh-CN.json`/`en-US.json` 同步新增 `historyRestore.*`。
- [x] 测试：`addToHistory`（trakt-client 表驱动）；`history-restore.ts` 服务
      层 11 个用例（trakt 来源候选/manual 来源候选/排序、恢复成功回填、
      unconfirmed、单条无 trakt id 判 failed、整批 Trakt 调用失败判 failed、
      重新拉取历史本身失败时全部判 unconfirmed）；两个新路由 7 个用例；新页
      面 20 个用例；`api.ts`/`queryKeys`/`remaining-hooks` 三层各自补测试。
- [x] **踩坑**：`restoreHistoryEntries` 第一版测试里给 `getHistory` 写了
      `mockResolvedValueOnce([]).mockResolvedValue([...])`，以为是在"跳过第
      一次调用"，实际上这个函数里 `getHistory` 只会被调用一次（对账那一
      次），`Once` 反而把真正需要的返回值吃掉了，导致本该成功回填的用例判
      成了 unconfirmed。删掉多余的 `mockResolvedValueOnce` 就好——这类"防御
      性"mock 链如果没有对应的真实调用次数，只会埋雷。

验收：api 842 个测试全绿，覆盖率 86.49/73.41/88.01/88.23，高于阈值
86/73/87/87；web 819 个测试全绿，覆盖率 86.82/81.8/83.79/88.17，高于阈值
86/81/83/87；两边 `tsc --noEmit`、`eslint` 均无报错；均未触发 ratchet。

## 收尾小结

两个批次全部完成：本地 `watch_history` 现在是真正的永久档案（唯一的自动清理
路径已删除，只剩用户在查重页/单条历史里主动确认过的删除会真正移除本地行）；
新增的恢复页面把"本地有、Trakt 没有"的记录暴露出来，用户确认后才会调用 Trakt
官方接口推回去——和查重/删除功能一样，全程没有任何自动触发的 Trakt 写操作。
